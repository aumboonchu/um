# SmartCart — Home, รายละเอียด และแก้ไข/ลบรายการซื้อ

## สิ่งที่เพิ่ม

- เมนู **ภาพรวม** เป็นหน้าแรก แสดงยอดซื้อ จำนวนรายการ ค่าเฉลี่ยต่อรายการ และจำนวนสินค้าของเดือนที่เลือก โดยแบ่งเดือนตามเวลาไทย
- แสดงรายการซื้อล่าสุดไม่เกิน 3 รายการ พร้อมไปหน้ารายละเอียดหรือประวัติทั้งหมด
- เปิดรายละเอียดจากประวัติหรือ Home: ชื่อ/SKU/UPC, ราคา จำนวน ยอดรวม ร้านค้า วันที่และเวลา และหมายเหตุ
- แก้ไขราคาซื้อจริง จำนวน ร้านค้า วันที่และเวลา และหมายเหตุได้ ใช้ชุดฟอร์มเดียวกับ Add Purchase
- เพิ่มช่องวันที่และหมายเหตุใน Add Purchase ด้วย ไม่แก้เฉพาะฟอร์มย้อนหลัง
- การลบมีหน้าทบทวนรายละเอียดและช่องติ๊กยืนยันก่อนส่ง ลบแบบ soft delete: ซ่อนจากประวัติและยอดรวม แต่เก็บแถวเดิมไว้
- หน้ารายละเอียดสินค้าแสดงสถิติการซื้อส่วนตัว ราคาต่ำสุด/สูงสุดที่เคยซื้อ และประวัติล่าสุดของสินค้านั้นไม่เกิน 20 รายการ พร้อมปุ่มบันทึกซื้ออีก
- ปุ่มกลับภายในเว็บย้อนจากสินค้าไปยังรายการซื้อก่อนหน้าได้ และเตือนก่อนทิ้งข้อมูลแก้ไขที่ยังไม่บันทึก

## ความถูกต้องและสิทธิ์

- ทุกยอดรวม ราคา และประวัติส่วนตัวคำนวณโดยกรองบัญชีจากเซสชันฝั่ง API ไม่รับ user_id จากผู้ใช้มาเชื่อถือ
- PATCH/DELETE ต้องมาจาก origin ของแอปที่ตั้งค่าไว้ และผู้ใช้ต้องเป็นเจ้าของรายการ
- ทุกการแก้ไข/ลบมี UUID และ expected revision ป้องกันกดซ้ำและแท็บเก่าบันทึกทับข้อมูลใหม่
- การเปลี่ยนรายการและการบันทึก mutation receipt อยู่ใน D1 batch เดียวกัน หาก receipt ล้มเหลว การเปลี่ยนรายการและร้านค้าจะ rollback
- เก็บเฉพาะข้อมูลคำขอที่ยืนยันและ UUID ที่รอผลใน localStorage แยกบัญชี/รายการ ไม่เก็บภาพ
- หากเน็ตหลุดหรือผลตอบกลับไม่ครบ จะแจ้งว่าไม่ทราบผลและให้ตรวจด้วยรหัสเดิม ไม่อ้างว่าล้มเหลวหรือสร้างคำขอใหม่ทันที
- หน้า Home แจ้งคำขอแก้ไข/ลบที่ยังรอยืนยันหลังรีเฟรช แม้รายการที่ลบจะหายจากประวัติแล้ว จึงยังตรวจ mutation receipt เดิมได้
- รายการที่ลบไม่ถูกนำกลับมาจากการ retry ของ offline create เพราะยังมีแถวเดิมและ sync ledger ป้องกันการสร้างซ้ำ
- ไม่ลบข้อมูลสินค้าอ้างอิง ประวัติของผู้อื่น หรือข้อมูล offline ที่รอซิงก์

## API และ migration

- `GET /api/v1/dashboard?month=YYYY-MM`
- `GET /api/v1/purchases/:id`
- `PATCH /api/v1/purchases/:id`
- `DELETE /api/v1/purchases/:id`
- `GET /api/v1/products/:id/detail`
- Migration `0006_purchase_management.sql`: เพิ่ม revision, deleted_at, last_mutation_id และตาราง purchase_mutations โดยไม่ลบแถวข้อมูลเดิม
- History และ My Products กรอง soft-deleted rows ออกจากรายการและสถิติ
- สำรองฐานข้อมูล staging เป็นไฟล์ส่วนตัวในเครื่องก่อน apply migration แล้ว ไฟล์สำรองและ wrapper QA ถูกแยกออกจากไฟล์เผยแพร่
- Staging Worker version: `aa086834-7b52-4a12-84e2-22d5e1763bff`; ไม่แก้ production

## ผลทดสอบ

- Web 182/182 และ API 152/152 รวม 334 รายการผ่าน; TypeScript และ release build ผ่าน
- ครอบคลุมการอ่านข้อมูลข้ามบัญชี, stale revision, UUID reuse, concurrent writes/retries, input validation, timezone boundary, soft delete, transaction rollback และ offline-create retry หลังลบ
- ทดสอบผ่าน UI จริงกับ API จริงที่ใช้ D1 จำลองในเครื่อง ไม่ใช้บัญชีหรือข้อมูล staging จริง
- ตัวอย่าง QA: ยอดรวม 99 บาท → แก้รายการจาก 74 เป็น 40 บาท → Home เหลือ 65 บาท → ยืนยันลบรายการ 40 บาท → Home เหลือ 25 บาท
- ตรวจ D1 QA พบ revision เพิ่มจาก 1 → 2 → 3, mutation receipt สองรายการ และแถวเดิมมี deleted_at; ข้อมูลบัญชีอื่นไม่เปลี่ยน
- ตรวจหน้าจอ 390 × 844 px ไม่พบ horizontal overflow และคืนค่าขนาดหน้าจอหลังทดสอบ
- การเผยแพร่ frontend ใช้ Verify และ Deploy web ใน GitHub Actions เดิม ต้องตรวจทั้งสองสำเร็จและตรวจเว็บจริงหลังเผยแพร่

## ขอบเขตที่ยังไม่รวม

- การแก้ไข/ลบต้องออนไลน์ ยังไม่เพิ่ม mutation ประเภทใหม่เข้า offline queue เดิม; offline capture ของรายการซื้อใหม่ยังทำงานเหมือนเดิม
- หน้า Home/รายละเอียดเก็บข้อมูลที่โหลดแล้วในหน้านั้นระหว่าง offline แต่ยังไม่ได้ทำ cache ประวัติทั้งหมดข้ามการเปิดแอปใหม่
- หนึ่งรายการซื้อยังหมายถึงสินค้าหนึ่งชนิด ไม่ใช่การจัดกลุ่มหลายสินค้าเป็นใบเสร็จเดียว ค่าเฉลี่ยจึงเป็นต่อรายการ ไม่ใช่ต่อการไปซื้อของหนึ่งครั้ง
- ยังไม่มีปุ่มกู้คืนรายการที่ลบใน UI และไม่มีการลบถาวร
- ไม่แก้ข้อมูลสินค้ากลางที่อาจใช้ร่วมกันระหว่างบัญชี; งานนี้เพิ่มหน้ารายละเอียดสินค้าและแก้ไขเฉพาะข้อมูลการซื้อส่วนตัว
- ยังไม่ได้ทดสอบครบเส้นทางบน Safari/Home Screen ของ iPhone จริง

ข้อควรระวัง rollback: อย่าย้อน Worker ไปยังรุ่นเก่าที่ไม่กรอง deleted_at หลังเริ่มมีรายการลบแล้ว มิฉะนั้นรายการที่ลบจะกลับมาแสดงในประวัติ/ยอดรวม ต้องคงการกรอง soft delete และตาราง mutation receipt ไว้
