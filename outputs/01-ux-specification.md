# SmartCart PWA — ลำดับ 1: UX Specification

## 1. วัตถุประสงค์

SmartCart เป็น PWA สำหรับบันทึกและติดตามการซื้อสินค้า ผู้ใช้สามารถสแกน UPC/Barcode เพื่อดึงข้อมูลสินค้าอัตโนมัติ บันทึกราคาที่ซื้อจริง ร้านค้า วันที่ และจำนวน ก่อนนำข้อมูลไปแสดงในหน้าแรก ประวัติการซื้อ และรายการสินค้า

เอกสารนี้กำหนด UX flow, หน้าจอ, สถานะ และกรณีผิดพลาดสำหรับ MVP โดยยังไม่ครอบคลุมรายละเอียดการเขียนโค้ด

## 2. ขอบเขต MVP

หน้าหลักของระบบประกอบด้วย:

1. Home
2. Scan Barcode
3. Add/Edit Purchase
4. History
5. Receipt Detail
6. Products
7. Product Detail
8. Sign in / Account

## 3. User Flow หลัก

```text
Home
  → Scan Barcode
  → ตรวจสอบ UPC ในฐานข้อมูล SmartCart
      ├─ พบสินค้า
      │    → Add Purchase พร้อมข้อมูลสินค้า
      └─ ไม่พบสินค้า
           → ค้นหาจาก Big C ด้วย UPC
               ├─ พบสินค้า
               │    → บันทึกสินค้าในฐานข้อมูล SmartCart
               │    → Add Purchase พร้อมข้อมูลอัตโนมัติ
               └─ ไม่พบ/Big C ใช้งานไม่ได้
                    → Add Product แบบกรอกเอง
                    → บันทึกสินค้าในฐานข้อมูล SmartCart
                    → Add Purchase
  → ตรวจสอบข้อมูลการซื้อ
  → บันทึก
  → Receipt Detail หรือ History
```

หลักการสำคัญคือทุกครั้งที่สแกน ระบบต้องค้นฐานข้อมูล SmartCart ก่อนเสมอ และเรียก Big C เฉพาะเมื่อเป็น UPC ที่ยังไม่มีในระบบ

## 4. Product Lookup

### 4.1 การสแกนครั้งแรก

1. รับค่า UPC จากกล้องหรือการกรอกเอง
2. Normalize ค่าโดยตัดช่องว่างและอักขระที่ไม่เกี่ยวข้อง
3. ตรวจสอบรูปแบบ UPC
4. ค้นหา UPC แบบ exact match ในฐานข้อมูล SmartCart
5. หากไม่พบ ให้ค้นหาที่ `https://www.bigc.co.th/search?q={UPC}`
6. ตรวจว่าผลลัพธ์ตรงกับ UPC ที่สแกน
7. เปิดหน้ารายละเอียดสินค้า
8. อ่านข้อมูล Product จาก JSON-LD เป็นแหล่งหลัก
9. อ่านข้อมูลเพิ่มเติมจากหน้าเว็บเมื่อ JSON-LD ไม่มี
10. Normalize และบันทึกสินค้าในฐานข้อมูล SmartCart
11. เปิดหน้า Add Purchase พร้อมข้อมูลที่ดึงมา

### 4.2 การสแกนครั้งต่อไป

- คืนข้อมูลจากฐานข้อมูล SmartCart ทันที
- ไม่เรียก Big C ระหว่าง flow การบันทึกตามปกติ
- แสดงวันที่อัปเดตข้อมูลสินค้าล่าสุด
- ระบบอาจอัปเดตข้อมูลต้นทางภายหลังแบบ background เมื่อข้อมูลเก่าเกินกำหนด
- การอัปเดตข้อมูลต้นทางต้องไม่ขัดขวางการบันทึกรายการซื้อ

### 4.3 ข้อมูลจาก Big C

ข้อมูลหลักที่ควรนำเข้า:

- UPC/GTIN
- ชื่อสินค้า
- แบรนด์
- รูปสินค้า
- ขนาดบรรจุ
- หน่วยขาย
- หมวดหมู่
- Big C product ID
- URL หน้าสินค้า
- ราคาอ้างอิง
- ราคาปกติก่อนส่วนลด
- สถานะสินค้า
- วันสิ้นสุดโปรโมชัน หากมี
- เลข อย. หากมี
- เวลาที่ดึงข้อมูล

ราคา Big C เป็นราคาอ้างอิงเท่านั้น เนื่องจากอาจเปลี่ยนตามเวลา โปรโมชัน และสาขา ผู้ใช้ต้องยืนยันราคาที่ซื้อจริงในหน้า Add Purchase

### 4.4 ลำดับความน่าเชื่อถือของข้อมูล

1. ข้อมูลที่ผู้ใช้ยืนยันหรือแก้ไข
2. ข้อมูลสินค้าในฐานข้อมูล SmartCart
3. JSON-LD จากหน้ารายละเอียด Big C
4. DOM จากหน้ารายละเอียด Big C
5. ข้อมูลจากหน้าผลการค้นหา Big C

การ refresh ข้อมูลจาก Big C ต้องไม่เขียนทับข้อมูลที่ผู้ใช้แก้ไขโดยอัตโนมัติ

## 6. Add/Edit Purchase

### 6.1 ข้อมูลที่กรอกอัตโนมัติ

- รูปสินค้า
- ชื่อสินค้า
- แบรนด์
- ขนาดบรรจุ
- หน่วยขาย
- หมวดหมู่
- UPC
- ราคาอ้างอิงล่าสุดจาก Big C หากมี
- แหล่งข้อมูลและวันที่อัปเดต

### 6.2 ข้อมูลที่ผู้ใช้ยืนยันหรือกรอก

- ราคาที่ซื้อจริง
- จำนวน
- ร้านค้า
- วันที่และเวลา
- หมายเหตุ

### 6.3 Validation

- ราคาที่ซื้อจริง: จำเป็น, มากกว่า 0 และมีทศนิยมไม่เกิน 2 ตำแหน่ง
- จำนวน: จำเป็นและมีค่าขั้นต่ำ 1
- ร้านค้า: เลือกจากรายการล่าสุดหรือกรอกใหม่
- วันที่ซื้อ: ค่าเริ่มต้นเป็นวันและเวลาปัจจุบัน
- หมายเหตุ: ไม่บังคับและต้องกำหนดความยาวสูงสุด
- ยอดรวม: คำนวณจาก `ราคาที่ซื้อจริง × จำนวน` ทันที

### 6.4 สถานะปุ่มบันทึก

- Disabled เมื่อข้อมูลจำเป็นไม่ครบ
- Enabled เมื่อข้อมูลผ่าน validation
- Loading ระหว่างบันทึกและป้องกันการกดซ้ำ
- Success เมื่อบันทึกสำเร็จ
- Error พร้อมปุ่มลองใหม่ โดยข้อมูลในฟอร์มต้องไม่หาย

หากผู้ใช้ย้อนกลับหลังแก้ไขข้อมูล ต้องแสดง confirmation ก่อนละทิ้งการเปลี่ยนแปลง

## 13. Error และ Fallback

| เหตุการณ์ | พฤติกรรม |
|---|---|
| UPC ไม่ถูกต้อง | แจ้งรูปแบบไม่ถูกต้องและให้สแกนใหม่หรือกรอกเอง |
| ไม่พบใน SmartCart | ค้น Big C อัตโนมัติ |
| Big C ไม่พบสินค้า | เปิด Add Product แบบกรอกเอง |
| Big C timeout/error | ให้ลองใหม่หรือกรอกข้อมูลเอง |
| พบหลายรายการ | ให้ผู้ใช้เลือกสินค้าที่ตรงกับ UPC |
| Big C ส่ง UPC ไม่ตรง | ไม่บันทึกอัตโนมัติและให้ผู้ใช้ตรวจสอบ |
| รูปโหลดไม่ได้ | ใช้ product placeholder |
| บันทึกไม่สำเร็จ | เก็บข้อมูลในฟอร์มและให้ลองใหม่ |
| Offline | ใช้ข้อมูลในเครื่องและเข้าคิว sync หากมี backend |
| ข้อมูลต้นทางเปลี่ยน | เก็บเวลาที่ดึงและไม่เขียนทับข้อมูลผู้ใช้ |

## 14. แนวทาง PWA และข้อมูล

- MVP ใช้แนวทาง local-first
- ผู้ใช้เริ่มใช้งานแบบ Guest ได้ เพื่อบันทึกข้อมูลในเครื่องแม้ยังไม่ได้เข้าสู่ระบบ
- Sign in with Google ใช้สำหรับ sync ข้อมูลข้ามอุปกรณ์และกู้ข้อมูลหลังเปลี่ยนอุปกรณ์
- อ่านและเพิ่มรายการได้เมื่อ offline
- หากมี backend ให้เข้าคิวและ sync เมื่อกลับมา online
- ไม่เก็บภาพจากกล้อง
- แสดง install prompt หลังผู้ใช้ได้รับคุณค่าจากระบบ เช่น หลังบันทึกรายการแรกสำเร็จ
- ข้อมูลราคาและโปรโมชันจาก Big C ต้องระบุว่าเป็นข้อมูลอ้างอิง

## 14.1 Sign in และ Account

### Sign in screen

ผู้ใช้เข้าหน้านี้ได้จาก onboarding, เมนู Account หรือข้อความแจ้งให้ sync ข้อมูล โดยมี:

- ปุ่ม `ดำเนินการต่อด้วย Google`
- Apple Login ถูกเลื่อนไป phase ถัดไป
- ข้อความว่า SmartCart ใช้ข้อมูลบัญชีเพื่อเชื่อมข้อมูลข้ามอุปกรณ์
- ลิงก์ Privacy Policy และ Terms of Service
- ปุ่มกลับไปใช้แบบ Guest หากยังไม่ต้องการเข้าสู่ระบบ

### Account states

| State | สิ่งที่แสดง | การทำงาน |
|---|---|---|
| Guest | `ข้อมูลอยู่ในอุปกรณ์นี้` | เริ่ม Sign in หรือใช้งานต่อแบบ local-only |
| Signing in | `กำลังเข้าสู่ระบบ…` | ป้องกันการกดซ้ำ |
| First signed-in session | `พบข้อมูลในอุปกรณ์นี้` | ให้เลือก `ซิงก์เข้า account` หรือ `เก็บไว้ในเครื่องเท่านั้น` |
| Signed in / synced | ชื่อหรืออีเมลที่ provider อนุญาตให้แสดง | Sync ข้ามอุปกรณ์และ Sign out |
| Offline guest | `บันทึกในเครื่องแล้ว · รอซิงก์` | ให้ใช้ได้ต่อ และแจ้งว่า Sign in ต้องใช้ Internet |
| Authentication error | ข้อความที่เข้าใจง่ายและปุ่มลองใหม่ | ไม่ลบข้อมูล IndexedDB |

### Merge data หลัง Sign in

1. ผู้ใช้เลือก Google และยืนยันตัวตนกับ provider
2. SmartCart กลับมาที่แอปพร้อม session ที่ปลอดภัย
3. ระบบตรวจพบข้อมูล Guest ใน IndexedDB ที่ยังไม่ผูกบัญชี
4. ผู้ใช้เลือกว่าจะ sync ข้อมูลนั้นเข้า account หรือเก็บเป็น local-only
5. หากเลือก sync ให้สร้าง operation UUID ต่อรายการและส่งผ่าน `/sync`
6. แสดง progress และจำนวนรายการที่เหลือ
7. ข้อมูลถือว่าปลอดภัยข้ามอุปกรณ์เมื่อ Worker ยืนยันว่าบันทึกเข้า D1 สำเร็จ

การ Sign out ต้องยกเลิก session บนเครื่อง แต่ต้องไม่ลบ pending offline data โดยไม่มี confirmation

## 16. Acceptance Criteria ของลำดับ 1

- ทุกหน้าจอหลักมี loading, empty, error และ offline state ที่เกี่ยวข้อง
- ระบบค้นฐานข้อมูล SmartCart ก่อน Big C ทุกครั้ง
- UPC ที่เคยนำเข้าแล้วไม่เรียก Big C ซ้ำใน flow ปกติ
- UPC ใหม่สามารถนำเข้าข้อมูลจาก Big C และบันทึกในฐานข้อมูลได้
- JSON-LD เป็นแหล่งหลักสำหรับข้อมูลสินค้า Big C
- หาก Big C ใช้งานไม่ได้ ผู้ใช้ยังสร้างสินค้าและบันทึกการซื้อได้
- ราคา Big C ไม่ถูกใช้เป็นราคาซื้อจริงโดยไม่ผ่านการยืนยันของผู้ใช้
- การ refresh ข้อมูลต้นทางไม่เขียนทับข้อมูลที่ผู้ใช้แก้ไข
- ข้อมูลในฟอร์มไม่หายเมื่อเกิดข้อผิดพลาดระหว่างบันทึก
- ผู้ใช้สามารถดู แก้ไข และลบรายการซื้อได้

## 17. ประเด็นที่ต้องยืนยันก่อนลำดับ 2

1. จะใช้ฐานข้อมูลในเครื่องอย่างเดียว หรือมี backend สำหรับ sync
2. ระยะเวลาที่ถือว่าข้อมูล Big C เก่า เช่น 7 หรือ 30 วัน
3. อนุญาตให้ผู้ใช้ refresh ข้อมูลสินค้าเองหรือไม่
4. การเก็บรูปสินค้า: อ้างอิง URL ต้นทางหรือดาวน์โหลดมาเก็บเอง
5. ต้องรองรับสินค้าเดียวกันจากแหล่งข้อมูลอื่นนอกจาก Big C หรือไม่
6. ต้องการเก็บประวัติราคาอ้างอิง Big C หรือเก็บเฉพาะค่าล่าสุด
7. ต้องตรวจสอบข้อกำหนดการใช้งานและข้อจำกัดในการเข้าถึงข้อมูลของ Big C ก่อนใช้งานจริง
