# SmartCart: Scan-first journey และรายงานแยกรอบซื้อ

วันที่ 28 ตุลาคม 2026

## Journey ใหม่

1. เปิดแอปมาที่ **สแกน / รอบนี้** (กล้องเริ่มเมื่อผู้ใช้กดอนุญาต/เปิดสแกนเท่านั้น)
2. สแกน UPC/EAN แล้วค้นฐานข้อมูล SmartCart อัตโนมัติ ไม่รอการ scrape ร้านค้า
3. ถ้าไม่พบ แสดงหน้าเพิ่มข้อมูลพร้อมบาร์โค้ดเดิม: ชื่อ แบรนด์ ขนาดบรรจุ หรือใช้ภาพ Big C / Makro Pro
4. เมื่อเพิ่มสินค้าแล้วกลับไปใส่ **จำนวนและราคาที่ซื้อจริง**
5. กด **เพิ่มเข้ารอบนี้ → สแกนต่อ** เพื่อเพิ่มรายการในตะกร้าของรอบนี้ ยังไม่สร้างยอดซื้อใน D1
6. แก้ไขหรือนำสินค้าออกจากรอบได้ก่อนชำระ
7. กด **ชำระเงิน / จบรอบนี้** ตรวจยอด ระบุร้าน วันที่ วิธีชำระ หมายเหตุ และติ๊กยืนยัน
8. เก็บทั้งรอบลง IndexedDB ก่อน แล้วซิงก์เข้า D1 เป็น transaction เดียว
9. ดู **รายงานรายรอบ** เลือกเดือน เปิดรายละเอียด และดาวน์โหลด CSV ของรอบนั้น

ปุ่มชำระเงินเป็นการบันทึกว่าผู้ใช้ชำระเองแล้ว ไม่ตัดเงินจริง ไม่เชื่อมระบบรับชำระ และไม่ใช่ใบเสร็จจากร้านค้า

## การบันทึกและข้อมูลเดิม

- เพิ่ม migration `0007_shopping_rounds.sql`: `shopping_rounds`, `shopping_round_lines` และคอลัมน์ `purchases.shopping_round_id`
- ไม่ลบ/อัปเดตประวัติเดิมเพื่อเดารอบซื้อ รายการเดิมยังมีรอบเป็น `NULL`
- รอบใหม่ใช้ UUID ทั้งรอบและแต่ละรายการ พร้อมตรวจ payload hash ฝั่ง D1
- Transaction บันทึก metadata รอบ สินค้าทุกแถว และ snapshot รายงานพร้อมกัน หากล้มเหลวต้องไม่มีเพียงบางสินค้าในรอบ
- รายงานเก็บชื่อ SKU UPC ขนาดและราคาขณะ checkout ไว้ ไม่เปลี่ยนตามการแก้ catalog ภายหลัง
- ซื้อหลายหน่วย/แพ็กในหนึ่งแถวได้ ขนาด `24.6 g x 12` จำนวนซื้อ 1 คือ 1 แพ็ก ไม่ใช่ 12 แพ็ก
- ยอดรวมคำนวณด้วยสตางค์ ฝั่ง API ไม่รับยอดรวมที่ client แต่งขึ้นมา
- ไม่ย้าย UUID รายการที่เคยบันทึกแล้วเข้ารอบอื่น
- รอบที่ชำระแล้วอ่านได้ แต่ไม่แก้/ลบรายชิ้นผ่าน API เพื่อไม่ให้ยอดรอบกับรายงานสินค้าคลาดกัน รายการเดิมที่ไม่ผูกรอบยังแก้/soft-delete ได้ตามระบบเดิม
- ยังคง API เดิมไว้รองรับข้อมูล/คิวเก่า แต่หน้าแอปใหม่ไม่สร้างรายการซื้อเดี่ยวเป็นทางหลักแล้ว

## แยกสถานะให้ชัดเจน

- **กำลังเลือกสินค้า**: เป็น draft บนอุปกรณ์ ยังไม่รวมยอดใช้จ่าย
- **จบรอบแล้ว รอซิงก์**: payload ทั้งรอบถูกเก็บแบบคงที่บนอุปกรณ์
- **บันทึกเข้า D1 แล้ว**: ยืนยัน receipt ที่มี UUID ยอดและจำนวนรายการตรงกัน แล้วเก็บ IndexedDB เป็น cache

ร่างและ outbox แยกตามบัญชี มีการตรวจบัญชีเจ้าของรอบซ้ำใน API ป้องกันคิวเก่าส่งเข้าบัญชีใหม่

IndexedDB ใช้ transaction และ revision ป้องกันหลายแท็บเขียนทับกัน เมื่อยอดถูกเปลี่ยนจากอีกแท็บ คำยืนยัน checkout เดิมใช้ไม่ได้ และฟอร์มแก้รายการเก่าไม่เขียนทับ revision ใหม่

เมื่อออนไลน์/เข้าสู่ระบบจะพยายามซิงก์อัตโนมัติ มีปุ่มซิงก์ด้วย UUID เดิมหากล้มเหลว รอบที่ยังไม่เข้า D1 อาจสูญหายเมื่อเว็บ/อุปกรณ์ล้าง storage ห้ามรับประกันว่าจะไม่สูญหาย ขอ persistent storage แต่ทำงานต่อเมื่อไม่ได้รับอนุญาตได้

## รายงาน

- เดือนใช้ขอบเขตเวลาไทย UTC+7
- ยอดชำระรวม จำนวนรอบ และค่าเฉลี่ยต่อรอบจาก D1
- รายการแยกรอบ: รหัสรอบ ร้าน เวลา วิธีชำระ จำนวนแถว และยอด
- รายละเอียดรายสินค้า: ชื่อ SKU UPC ขนาด จำนวน ราคาต่อหน่วย ยอดแถว และหมายเหตุ
- รายการเดิมที่ไม่ผูกรอบและยอดของรายการเดิมแสดงแยก ไม่รวมเป็นจำนวนรอบ
- รอบรอซิงก์แสดงอีกส่วน ไม่บวกเข้ายอดยืนยัน D1 ซ้ำ
- CSV แบบ UTF-8 มี BOM และป้องกัน formula injection สำหรับช่องข้อความ
- ขณะออฟไลน์แสดงเฉพาะ cache ที่มีบนอุปกรณ์ ไม่อ้างว่าเป็นประวัติครบทุกเครื่อง
- ภาพรวมเดิมยังสรุปยอดจากแถวซื้อที่ยืนยันแล้ว (รวมทั้งรายการเดิมและแถวในรอบใหม่) แต่จำนวน/เฉลี่ยของหน้านั้นเป็นต่อแถวสินค้า ส่วนค่าเฉลี่ยต่อรอบอยู่ในรายงานรายรอบ

## API ใหม่

- `POST /api/v1/rounds/checkout` — auth + trusted Origin + account owner + body/field/amount bounds; รอบละ 1–100 แถว
- `GET /api/v1/rounds?month=YYYY-MM&cursor=...` — auth, pagination 20 รอบ, totals เฉพาะบัญชี
- `GET /api/v1/rounds/:id` — auth, ไม่เปิดเผยรอบของบัญชีอื่น
- `GET /api/v1/products/upc/:upc?databaseOnly=1` — ค้น catalog เท่านั้น ถ้าไม่พบคืน 404 โดยไม่เรียก Big C
- Manual product registration รองรับ `packageSize` เพิ่มเติม

## Deployment และข้อควรระวัง

- Migration 0007 ใช้กับ D1 **staging** สำเร็จแล้วแบบ additive
- Worker staging version: `7f3e83fc-bf0e-46f5-8f7a-9e29690170ad`
- ไม่แตะ production ไม่เปิด Apple Login หรือแพ็กเกจเสียเงิน
- ไม่ส่งออกฐานข้อมูลทั้งชุดเป็นไฟล์ใหม่: ถูก auto-review ปฏิเสธเพราะอาจมีข้อมูลส่วนตัว/บัญชี และไม่ได้ลองส่งออกทางอื่น
- การอ่าน bookmark Time Travel ได้ authentication error จึง **ยังไม่ได้ยืนยันจุดกู้คืน**; คำสั่ง list/apply migrations และ deploy staging ทำงานได้
- ห้าม rollback API ไปเวอร์ชันที่ไม่รู้จักรอบซื้อ/ไม่ล็อกแถวที่ชำระแล้ว เพราะอาจแก้รายชิ้นจนยอด snapshot ไม่ตรง; คง API ที่รองรับ migration 0007 ไว้
- npm audit ยังแจ้งช่องโหว่ใน dev/test toolchain เดิม เช่น Vitest/tinypool และ Workers test dependencies รวมถึง Hono advisory เดิม (แอปไม่ได้ใช้ JSX boundary หรือ serveStatic ที่ advisory อ้างถึง) งานนี้ไม่อัปเกรด major toolchain แบบอัตโนมัติ ควรติดตามแก้แยกก่อน production
- การเปิดแอปใหม่ขณะออฟไลน์ยังต้องตรวจ auth ออนไลน์ก่อนเข้าถึงบัญชี; offline journey รองรับเมื่อบัญชีตรวจยืนยันในแอปที่เปิดอยู่แล้ว
- ยังไม่มีการแก้ไข/ยกเลิกทั้งรอบหลังชำระ, ส่วนลดระดับบิล, ภาษี, หลักฐานการจ่าย หรือการรับเงินจริง
