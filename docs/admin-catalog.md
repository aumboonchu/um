# ผู้ดูแลสินค้า

## การใช้งาน

เข้าสู่ระบบด้วยบัญชี Google ของเจ้าของระบบ → สินค้า → เลื่อนล่างสุด → ผู้ดูแลระบบ

ใส่รหัสเริ่มต้นที่ได้รับ แล้วตั้งรหัสใหม่อย่างน้อย 8 ตัวอักษร ยืนยันให้ตรงกัน ก่อนดูหรือแก้สินค้ากลางได้ ผู้ใช้ทั่วไปไม่เห็นปุ่มและไม่มีสิทธิ์เรียก API ผู้ดูแล แม้ทราบรหัสเริ่มต้น

ค้นหาสินค้าทั้งระบบด้วยชื่อ แบรนด์ SKU หรือบาร์โค้ด รวมถึงสินค้าที่ยังไม่เคยซื้อ โหลดครั้งละ 30 รายการ เปิดสินค้าเพื่อดูข้อมูลระบบและแก้ชื่อ แบรนด์ ขนาด หน่วย และหมวดหมู่

การแก้ไขมีผลต่อข้อมูลสินค้ากลาง ไม่แก้ SKU/UPC ไม่เปลี่ยนยอดซื้อหรือใบสรุปรอบที่ชำระแล้ว และไม่ล้างข้อมูลที่แต่ละบัญชีปรับไว้เอง

ต้องออนไลน์เพื่อใช้งาน รหัสผ่านและสิทธิ์ผู้ดูแลไม่ถูกเก็บใน browser storage สิทธิ์มีอายุ 15 นาที ผูกกับ Google session เดิม และออกจากสิทธิ์เมื่อปิดหน้าผู้ดูแล โดยไม่ออกจาก Google

## การตรวจยืนยันผล

ก่อนส่งการแก้ไข เก็บข้อมูลและ UUID ของคำขอเฉพาะบัญชีลงเครื่อง โดยไม่มีรหัสผ่านหรือ admin token หากเก็บไม่ได้จะไม่ส่งคำขอ

หากคำตอบหายหรือหมดเวลาระหว่างบันทึก ระบบไม่อ้างว่าสำเร็จ ให้กลับมาใส่รหัสผู้ดูแลและตรวจด้วย UUID เดิม ป้องกันการแก้ซ้ำเป็นคำขอใหม่ ถ้าข้อมูลถูกแก้จากหน้าหรือเครื่องอื่น ต้องโหลดข้อมูลล่าสุดและตรวจสอบก่อนบันทึกใหม่

## การรักษาสิทธิ์

- Migration `0010_admin_catalog.sql` เพิ่มตารางสิทธิ์/session/audit และ revision ของสินค้า ไม่มีการเปลี่ยนหรือลบรายการซื้อเดิม
- ไม่เปิด endpoint สมัคร admin หรือกำหนดสิทธิ์เอง และไม่ให้สิทธิ์แก่ผู้เข้าคนแรก
- ผู้ดูแลต้องเป็น existing user ID ที่ผู้ดูแลระบบ provision แยกต่างหาก ไม่เทียบอีเมลจาก input เพื่อให้สิทธิ์ขณะใช้งาน
- รหัสผ่านใช้ salted PBKDF2-SHA256 100,000 iterations ตามข้อจำกัด runtime ที่ใช้ เป็นชั้นเพิ่มจากบัญชี Google ที่กำหนดไว้ ไม่ใช้รหัสสี่หลักเพียงอย่างเดียว
- เปรียบเทียบ hash แบบ timing-safe; token สุ่ม 256 บิต เก็บเฉพาะ SHA-256 ใน D1
- รหัสเริ่มต้นให้สิทธิ์ตั้งรหัสใหม่เท่านั้น อายุ token เริ่มต้น 5 นาที การเปลี่ยนรหัสหมุน credential revision และยกเลิก admin token เดิมทั้งหมด
- จำกัดการลองเข้าสู่ผู้ดูแล 5 ครั้งต่อ 15 นาทีต่อบัญชีแบบ atomic รวมการเข้าสำเร็จ ไม่ใช้ตัวนับเฉพาะ browser
- ทุกคำขอเขียนต้องมี Origin ตรงกับแอป; ตรวจบัญชี Google, admin token, session ต้นทาง, อายุ และ credential revision ฝั่ง API
- การแก้ข้อมูลและ audit before/after อยู่ใน D1 batch เดียว มี optimistic revision และ receipt UUID; audit ไม่ถูกส่งให้ผู้ใช้ทั่วไป
- หากลืมรหัส ยังไม่มีหน้ากู้รหัสอัตโนมัติ ต้องให้ผู้ดูแลโครงสร้างระบบช่วยดำเนินการ ไม่คืนกลับรหัสเริ่มต้นอัตโนมัติ
